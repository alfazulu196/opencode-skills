# Релизный пакет фич

Проверенный ритм полевого проекта: правки накапливаются «пакетом»,
выпускаются одним циклом.

## Составление пакета

1. Собрать карту кандидатов (что просит поле + что выявил дебрифинг).
2. Отметить **полевые зависимые** пункты (нужны данные с выезда:
   реальные фото для bench, живые ошибки для few-shot) — их в пакет
   кода не класть, готовить инструменты сбора данных.
3. Принципы: офлайн без облака/логина/синхронизации; **ноль новых
   зависимостей** (проверять, нет ли пакета уже в бандле транзитивно —
   см. скилл `pyinstaller-windows`).
4. Каждая фича — с тестами сразу; «сделаем всё» → делать всё по очереди,
   мелкими завершёнными этапами (сервис → UI-кнопка → тесты → ruff).

## Порядок выпуска

1. Полный `pytest` + `ruff check` (не только новые файлы).
2. `APP_VERSION` поднять (semver: патч — грабли/мелочи, минор — фичи).
3. Документация: CHANGELOG (по-человечески, от поля), README,
   ПАСПОРТ/спецификация требований (новые FR с номерами — закрывать
   существующие, не плодить).
4. Коммит: сообщение через **`git commit -F файл`** (PowerShell портит
   кириллицу), тело — список фич.
5. **Свежий бандл**: `git bundle create backup/repo-YYYYMMDD.bundle --all`
   — до любого пуша/ребейза.
6. Пуш в оба облака (см. скилл `git-dual-cloud`).
7. **Пересборка обеих поставок** (onefile + onedir) — фоном в конце
   пакета; самотест запуском, «Версия сборки» сверить с APP_VERSION.
8. Дебриф-данные с выезда (`data/logs/*.jsonl`) — отдельный цикл:
   `python -X utf8 tools/debrief_report.py` → отбор худших кадров →
   bench → правка промпта (см. скилл `offline-llm-ollama`).

## Полевое правило

Перед выездом **не пересобирать** и не менять рабочий exe: проверить,
что версия на машине = проверенной сборке. Правки в пакете — только
после возврата с поля (дебрифинг даёт материал для следующего пакета).

## Инструменты репродукции

Скрипты-репродукции писать во временную папку (`%TEMP%\opencode\*.py`,
UTF-8), не засоряя репо: мини-программы для изоляции багов (например,
QPdfWriter access violation) — их же использовать для сравнения
«до/после» фикса. Отладочный скрипт ценнее ментальной модели: если
«очевидная» причина не воспроизводится минимальным скриптом — гипотеза
неверна, продолжать сужение.
